# 流程与协作效率审计 · 2026-08-28

> 结论类型：仓库事实 + 专家启发式评审。本审计不把 CI 通过写成产品验证。Alan 在审阅初稿后明确指出：他的验证速度快于候选交付速度；以下结论已据此修正。规范性调整已同步写入 [`COLLABORATION_PROTOCOL.md`](COLLABORATION_PROTOCOL.md)。

## 一句话结论

当前流程的工程防错能力已经较强，主要效率瓶颈是：**实现批次太大，使可玩候选交付慢于 Alan 的验证速度；同时需求与优先级散落、PR 粒度两极化、文档同步成本持续上升。**

近期默认目标应从“继续扩充内容”切换为“更快交付一个 clean 候选给 Alan 验证，并据此决定下一轮只改什么”。独立外部玩家证据是另一类门禁，不能用它抹掉或贬低 Alan 已提供的真实玩家证据。

## 当前实际流程

目前协作大致按以下链条运行：

1. Alan 提出体验、缺陷或方向；
2. Codex 从多份设计、计划、证据和历史文档中恢复上下文；
3. 将问题拆为聚焦分支／worktree，补实现、自动回归和文档；
4. 推送 PR，等待 Web、Godot 和 clean Web candidate 门禁；
5. 很快合并到 `main`，`main` 再跑一次质量门禁；
6. 需要时生成桌面 artifact，再由 Alan 或玩家实测；
7. 将新事实同步回 README、规格、构建记录、试玩记录和讨论日志。

这个流程对存档、构建来源、资源闭包和回归错误很谨慎；但第 2、5、7 步的协调成本偏高，第 6 步发生得太晚。Alan 收到可玩候选后可以很快给出有效反馈，真正拖慢闭环的是实现范围、集成和交付准备。

## 效率瓶颈与优先级

| 优先级 | 瓶颈 | 现象 | 实际代价 | 处理方向 |
| --- | --- | --- | --- | --- |
| P0 | 候选交付慢于 Alan 验证 | Alan 已快速验证过多个实际版本；本轮同时推进 24 关、30 条事件、系统合同和表现层后，迟迟没有形成新的 clean 可玩候选 | Alan 无法及时纠偏，反馈到下一候选的周期被实现、集成和文档工作拉长 | 缩小实现批次；先交付 clean 候选给 Alan，收到反馈后只修一个核心问题 |
| P0 | 没有唯一活跃优先级视图 | P0/P1/P2 分布在 README、共识、反馈计划、发行清单、设计日志等处；部分文档已过时或明确废止 | 每次任务都重新考古；旧 P0 与新 P0 同名，完成状态难以判断 | 每轮只指定一个“当前执行视图”；最多 1 个核心学习目标、3 个 Now 项，其余只进入 Next/Later |
| P1 | 独立新玩家证据不足 | Alan 的创作者／产品负责人实机证据真实有效，但不能单独回答陌生玩家是否无提示理解、是否愿意继续或购买 | 新手可读性和市场判断仍可能被开发背景影响 | Alan 先快速验方向；代表切片稳定后再交给 3～5 名未参与开发的玩家，不让招募阻塞每次内部迭代 |
| P1 | PR 粒度两极化且评审不足 | 一端是数百文件的大 PR，另一端是数分钟内连续合并的修补／文档 PR；最近 12 个 PR 无 review | 大 PR 难以复核，小 PR 增加 CI、合并、文档和上下文切换；缺陷更多依赖后续试玩暴露 | 按“一个可独立验收的玩家问题”组包；同一问题的实现、测试和事实更新留在同一 PR；合并前做风险分级自审 |
| P1 | 文档写放大 | 同一实现事实经常同步到 README、BUILD_MANIFEST、RELEASE_CHECKLIST、PLAYTEST、讨论日志和多个规格 | 改一处要维护多处，仍会产生陈旧事实；阅读入口越来越长 | 规格只写规则，执行视图只写状态，日志只写历史，README 只写入口与当前摘要；不在所有文档复述同一状态 |
| P2 | CI 有重复与例外风险 | PR 与 `main` push 双跑；不同 job 重复安装／下载／构建；CI 配置和分类脚本自身被判为轻量改动 | 消耗 runner 时间并延长高频 PR 队列；gate-only 修改可能没有执行完整路径 | 先减少 PR 数；保留 `main` 安全复跑，直到有强制分支保护；CI 自身改动至少在合并前手动或临时强制跑一次完整路径 |
| P2 | 工作区卫生依赖人工纪律 | 活跃分支落后主线且 dirty；大量 prunable worktree 记录和旧本地分支 | 容易打开错误版本、基于旧线继续写、误判提交或 artifact 来源 | 每轮开始输出绝对路径／分支／SHA；合并后统一归档或清理已确认无用的 worktree 与分支 |

## 需求拆分：哪里有效，哪里失真

现有协议提出“感觉 → 候选 → 实验 → 承诺”，并要求一轮只验证一个核心问题。这是正确的拆分轴。实际执行的偏差主要有两种：

1. **按系统和内容量拆，而不是按待验证假设拆。** 商业候选、24 关战役、30 条事件、四季结果图一起推进，单个 PR 虽有工程边界，却同时改变了过多玩家体验前提。
2. **缺陷链拆得太碎。** HUD 遮挡、模态输入、导航目标、任务标记等连续成为多个快速 PR；它们都围绕“玩家能否看清并完成当前任务”，更适合作为一条验收链集中收口。

默认拆分单位应改为：

```text
一个玩家问题
→ 一个可证伪假设
→ 一个最小可玩切片
→ 自动排雷
→ Alan 快速验证
→ 需要时再做独立外部玩家验证
→ 继续、修正或停止
```

只有音频盲听、跨平台验证、只读审计、独立资产实验等不改变彼此前提的任务才并行。内容生产不能仅因数据结构支持批量生成就提前并行。

## CI 判断

CI 目前是项目的强项，不是首要瓶颈：Node、Godot、资源闭包、clean Web candidate、桌面双平台 artifact 与哈希链覆盖面都较好，完整 PR 的等待通常只有数分钟。

需要注意三点：

- **CI 证明实现一致，不证明产品成立。** Alan 的实机反馈是有效真人证据；独立玩家再补充陌生人理解和市场外推。增加自动测试无法替代其中任何一层。
- **PR 与 main 双跑现在仍有安全价值。** 私有仓库当前无法通过现有 GitHub 计划读取／配置 branch protection；在规则不能强制执行时，不建议为了省几分钟直接取消 main 复跑。
- **轻量分类器的信任边界要更窄。** Markdown-only 跳过重任务合理；但 `.github/workflows/quality.yml` 与分类脚本自身也总被归为轻量，修改完整路径时可能只证明分类器自测，而没有证明重任务能启动。CI 基础设施 PR 应显式取得一次完整运行证据。

因此 CI 的近期优化顺序应为：减少无意义 PR 次数 > 缓存 Godot／模板和消除 job 内重复构建 > 在具备强制保护后再评估取消 main 重跑。

## 建议的近期运行方式

### 当前唯一 P0

把当前 HUD／输入合同安全地基于最新 `origin/main` 收口，尽快生成一个有精确 SHA 的 clean 候选；随后：

1. Alan 验证立春、雨水、谷雨和一次高潮，记录理解、卡点、节奏与“是否想继续”；
2. Codex 在下一小批候选中只处理一个核心问题，不把多轮反馈攒成大包；
3. Alan 接受代表切片方向后，可继续下一个有限切片；同时让至少 3 名未参与开发的玩家完成第一小时观察，达到已有计划要求时再扩到 5 人；
4. 独立玩家证据用于检查陌生人理解和外推风险，不重新判定 Alan 是否属于“真人验证”。

在 Alan 尚未收到并验证本轮 clean 候选前，不继续横向扩产。Alan 接受代表切片后可以推进下一有限切片；其余 330 条事件的批量生产、下一款游戏和批量终稿美术仍保持 Later，直到独立玩家证据支持规模化。

### WIP 与 PR 限制

- 同时最多 1 条实现主链；另可有 1 条不改同一前提的验证／研究任务；
- Now 最多 3 项，每项必须有完成证据和停止条件；
- 同一玩家问题的代码、测试、截图和事实更新放在同一 PR；不为每次文字同步另开即时 PR；
- 大于约 30 个文件或同时跨玩法、美术、音频、存档三类以上的 PR，默认先拆出代表切片或写明不可拆的因果链；
- 合并前至少做一次“从玩家问题反读 diff”的自审；高风险存档、输入、发布和证据链再做独立复核。

### 每周只看五个指标

| 指标 | 目的 |
| --- | --- |
| 从任务开始到交给 Alan 的 clean 候选时间 | 衡量当前主要瓶颈 |
| Alan 从收到候选到给出结论的时间 | 正确区分交付慢与验证慢 |
| 取得独立新玩家证据的假设数 | 衡量可向陌生玩家外推的产品学习 |
| 因方向变化被丢弃／重做的生产量 | 监控过早扩产 |
| PR 后发现的 P0/P1 与错误 artifact 次数 | 监控工程与交接质量 |

PR 数、提交数、测试数和已写事件数只作容量信息，不作为进展主指标。

## 成功判据

流程改进不是“文档更整齐”就完成。连续两轮满足以下条件，才算瓶颈开始解除：

- 每轮能指出唯一核心假设和唯一当前执行视图；
- 每个小批次扩展前已经取得 Alan 对前一候选的直接验证；批量扩产前另有独立玩家证据；
- 同一问题没有被拆成多个无需独立验收的连续 PR；
- 交付时能直接说清正确路径、分支、SHA、artifact、已验证与未验证；
- 稳定规格不再记录瞬时分支状态，活跃状态也不再散写进多个历史文档。


## 2026-09-10：按影响范围触发 CI

Alan 在授权四季制作后要求持续评估 CI 的必要性与触发条件，避免无关阻塞。实际检查发现此前只有“文档／全部”两档：独立春季 GDScript 也会跑网站构建、全部游戏回归、下载导出模板，再串行重建 Web 包；PR 合并后主线 push 还重复触发同一链。

Codex 本轮采用以下分流，保持现有 job 名称，便于识别检查结果：

| 改动 | 必要检查 |
| --- | --- |
| 文档与 CI 分流本身 | diff、分流测试；工作流结构本地核查 |
| 独立雨水／春季／全年场景、日历、驱动与对应测试 | 相关 Godot 路线／存档测试；全年测试存在后自动纳入；保留导出资源边界检查 |
| 共享游戏脚本、字体、资源或测试执行器 | 完整 Godot 回归与导出资源边界 |
| 网站／依赖／Node 测试 | 网站构建、lint 与 Node／美术合同测试 |
| 共用数据 | Godot 全套及 Node 合同所在 Web 套件 |
| 项目入口／导出配置／打包来源脚本或未知路径 | 全套及干净 Web 导出 |
| 手动阶段集成 | 所有检查，无条件完整覆盖 |

只在 PR 自动运行，手动 `workflow_dispatch` 用于阶段集成；取消合并后重复重型 push 触发。相同 PR 新提交取消过时运行。空变化集、无法确认 diff 或未知路径按全套处理，重命名检查两侧路径，网站源码中的 MDX 不走纯文档豁免。当前没有正式发行版，仍不自动上传候选包；这不等于放弃打包验证。

测试执行器增加 Python 标准库超时封装，macOS 没有 GNU timeout 时也能终止卡住的测试子进程组，并以 124 失败返回；成功标记与 SCRIPT ERROR 检查继续保留。路线测试运行模式只缩小选择范围，不放宽断言。原生性能／画面检查仍由每次相关绘制变更本地执行并归档，不能拿 headless 通关代替帧率证据。

Codex 负责本轮分流、混合路径／未知路径／重命名两端测试，超时正常退出与失败退出验证，以及实际路线测试运行；本轮 PR 验证执行器的完整 Godot CI。下一检查点为全年入口接入：检查该批触发范围是否覆盖内容、存档、画面和性能，必要时调整分类；发现漏测依赖则拓宽相应路径，不恢复所有改动无差别重跑。既有单一 Now 仍在战役规格，未新增任务队列。
