# 《一会儿巢里见》试玩证据与记录

历史会话保留当时构建中的旧展示名；从春季往返产品纵切起，新生成的玩家材料和应用显示统一使用《一会儿巢里见》，稳定产品 ID 与旧包文件 stem 暂不迁移。

本文件管理三条不能互相替代的证据流：Alan 本人自测、未参与策划／开发的外部玩家试玩、真实 Windows 设备检查。同一人在真实 Windows 设备上的外测可以同时产生两类记录，但结论仍要分别汇总；开发者自测永远不能计入外部玩家样本。

2026-08-21 的两分钟选择题问卷已被本轮证据包取代。旧问卷把预设的紧张点、正确行为和机制名塞进选项，只能测“玩家是否同意选项”，无法证明首分钟实际发生了什么；原来的 `3/5` 主动撤离与重开比例也不再作为当前版本的单一通过门槛。

## 生成一次匿名证据包

在与候选构建对应的仓库提交上执行：

```bash
npm run playtest:prepare -- \
  --task A \
  --tester-relation external_player \
  --candidate-commit <游戏内显示的提交号> \
  --candidate-clean \
  --artifact-sha256 <发给玩家的安装包 SHA-256>
```

默认输出到 `outputs/playtest-evidence/<随机会话号>/`，每位参与者单独生成一包，不覆盖上一位。`--tester-relation` 必须由协调者在生成时声明为 `external_player` 或 `alan_self_test`，参与者页面不能自行选择或改写身份。生成器会从候选提交中的 `package.json` 读取版本，验证并保存完整提交号，同时记录当前工具提交和 dirty 状态。使用 `--candidate-commit` 时必须显式二选一：CI／固定 artifact 用 `--candidate-clean`；确实来自未提交工作区的候选才用 `--candidate-dirty`。若省略候选提交，则直接使用当前 `HEAD` 及其真实 dirty 状态。安装包 SHA-256 必填，但生成器只记录这项绑定声明，不读取或计算安装包；协调者必须先用 sidecar 或本机哈希工具确认它与玩家实际收到的文件一致。

以上是保持兼容的 **A 包**身份流程。B 包不接受 `--artifact-sha256`、`--candidate-commit`、`--candidate-clean` 或 `--candidate-dirty`；它只接受 `--slice`、最终 distribution 的绝对 `--artifact` 路径和同一最终包的绝对 `--artifact-manifest` 路径，并从实际 artifact bytes、schema v1 manifest 与 manifest 精确提交中的 catalog bytes 重新推导身份。A 的声明式旧流程与 B 的固定 artifact 流程不能混用。

输出严格分成两部分：

- 只把 `participant/` 文件夹交给参与者，其 `index.html` 是 6 项短表（4 个原话题、2 个结束选择），无网络依赖，可在本机保存并导出匿名 JSON；
- `coordinator/` 只给 Alan／测试协调者；其中 `observer.html` 单独记录环境、相对时间和机制接触状态，另含构建清单和分析模板。参与者页面不会链接、加载或复制这些内部问题。

输出目录带专用 sentinel。生成器只会替换自己创建的目录，拒绝仓库、源码目录、文件系统根目录和没有 sentinel 的现有目录。

## 三种互不混做的任务包

### A：首次体验

- 每位未参与开发的玩家只从标题开始玩首节点，T0 为首次取得控制权，最多 15 分钟；
- 开始前不解释操作、目标或设计意图。玩家明确求助后可给最少必要帮助，但必须记录其求助原话和相对时间；
- 参与者结束后只填写首分钟回忆、最远画面、最卡／意外之处、一句话总结、结束原因和重玩意愿，不逐项自评机制；
- 协调者／观察者在隔离的 `observer.html` 记录试玩前是否有游戏外解释，以及第一次交蜜、完成条件、传粉、急转、饮蜜、失败与重开，并区分未观察、未到达、尝试未完成、依赖游戏提示、游戏外帮助和独立完成；
- 远程没有观察或匿名录屏时，机制状态必须标为“没有可用观察，不能判定”，不能让参与者补做长表，也不能把未知误算成没看懂；
- 当前正常首轮路线没有稳定的“三分钟后再次急转”机会。observer 必须把复测机会和复测结果分开记录：只有首次急转后约三分钟、同一危险语法、没有重新教学的 `provided_stable` 机会及其观察结果，才能评价迁移；未观察、首次未完成、没有机会或重新教学后一律不可判定，不能写成迁移失败。

参与者只回答不泄题的短自由回忆：

- “开始后一分钟，你先做了什么？有没有不知道下一步做什么、操作没有成功或停下来想的地方？”
- “你最远到达了什么画面？”
- “哪一处最难懂、最难操作、最意外，或者最想让我们知道？”
- “用一句自己的话描述这次游戏。”

这里把口语里的“卡”拆成“不知道下一步”“操作没有成功”“停下来想”“难懂／难操作”，避免参与者把理解、执行和停顿混为一个模糊结论；字段名、六项结构和 JSON schema 不变。A／B 使用同一份参与者短表，问题仍只收自由回忆，不提示具体机制、正确操作或成功条件。

### B：单个高级切片（源码防护已就绪；新 artifact／新会话与有效运行结果待补）

生产源码已完成 B01 的独立 typed scene、固定身份链、启动 fail-closed 与精确 ready receipt。最近双端 artifact／Alan 包来自早于 PR #90／#91 的 `57aefc4`，只作下文历史错配记录；下一次有效 B01 的 artifact、session／ticket 与运行结果尚未生成：

- `godot/data/playtest_slices.json` 的公开 schema v1 只含中性编号、公开任务文案、时限和状态；生产 catalog 唯一条目是 `B01 / 固定切片 B01 / 10 分钟 / ready`，不含机制名、scene、handler、stage、seed、存档路径或 patch／override；编译期 registry 直接 preload B01 scene，不从 ticket 或 catalog 接受路径；
- 导出主入口是 bootstrap。没有 user argument 且 raw engine arguments 也没有 ticket 时仍实例化原 `main.tscn`；试玩的完整启动命令必须是 `"<游戏可执行文件的绝对路径>" -- "--playtest-ticket=<playtest-ticket.json 的绝对路径>"`，其中 `--` 把唯一一个 user argument 与引擎参数分开。若 ticket 被错误放在分隔符前，bootstrap 必须显示稳定错误码 `PT-ARG-SEPARATOR`，不得静默进入 Main。ticket、同目录固定名 `artifact-manifest.json`、包内 build provenance、运行平台、产品版本、完整 clean commit、artifact 字段、catalog 原始字节 SHA-256 和编译期 registry 任一不一致都会 fail closed；
- 每次正确测试必须生成新的 session／ticket，不得复用旧会话。仓库启动助手会先清除该 ticket 同目录的固定旧 `playtest-ready-receipt.json`，始终插入 `--`，并只在 B01 typed scene 完成配置且真正进入场景树、receipt 的 session／slice／commit／ticket SHA-256 全部匹配后报告 `Playtest ready receipt verified`。该 receipt 是启动链机器证据，不是玩家完成、理解或迁移证据；它不使用 SaveManager，也不读写普通或试玩存档；
- B01 使用与主流程共享的急转输入与因果规则，但不实例化 Main、MentorTutorial 或 SaveManager，也不读写任何存档。基础设施仍能为其他未来切片从 ticket 原始 bytes 派生隔离 namespace，但 B01 本身不走存档流程；
- B01 的时序固定为：2.8 秒老师傅因果示范 → 有界引导模仿（最多 90 秒或 4 次有效机会）→ 无提示实践（最多 90 秒或 3 次机会）→ 实践首次成功后恰好 180 秒 active 花间路线 → 恰好一次无字、同配置复测 → 中性结束。暂停或失去焦点不计入 180 秒 active 时钟；内部结果互斥为 `completed_independent`、`attempted_incomplete` 或 `not_attempted`，玩家端不显示通过／失败评价或重试引导；
- B 生成器读取实际 distribution bytes，严格复核 manifest 的文件名、平台、大小、SHA-256、版本、完整提交和 `dirty:false`，计算 manifest 自身 SHA-256，再以 `git show <manifest commit>:godot/data/playtest_slices.json` 读取精确 catalog bytes。只有 artifact 与该精确 clean commit 中的 `ready` catalog 一致时才会生成输出。

所有 B 包在启动前必须由协调者只说一句流程说明：“这是一段约10分钟的实际试玩；按画面行动，结束后再填表”。这句话只确认当前任务、预计占用和填表顺序，不得解释机制、操作答案、成功条件或画面含义。若协调者没有先说明“现在要实际试玩”，参与者据界面或交接信息合理关闭程序，应记为 **playtest protocol / instruction failure**；不得据此填 `not_attempted`、判定未学会或形成任何机制结论。重新启动后的记录必须注明是否为程序性重试，不能冒充完全盲测。

下列命令格式只能用于**从最终 clean commit 新建并已校验的 artifact**：

```bash
npm run playtest:prepare -- \
  --task B \
  --slice B01 \
  --tester-relation external_player \
  --artifact /absolute/path/NamelessBecoming-macOS.zip \
  --artifact-manifest /absolute/path/NamelessBecoming-macOS.zip.manifest.json
```

## 时间、原话与隐私

- observer 事件时间都是 `T+mm:ss`，其中 `T0 = 首次取得控制权`。远程无观察、无录像时选择“未观察／时间不可得”，不得伪造精确秒数；
- participant 导出只含构建来源、生成时固定的匿名会话代号和关系类型、4 个原话字段及 2 个结束选择；设备、机制接触状态与时间线只进入 observer 导出；
- 协调者收到两份 JSON 后，在内部模板中分栏保存：客观观察事实、玩家逐字原话、开发者解释、后续行动。participant 短表本身不能证明机制掌握；不得把玩家原话润色成开发者结论；
- 不收姓名、联系方式、账号、IP、年龄、性别、精确位置、健康／残障信息、脸或声音；
- 若参与者自愿匿名录屏，必须先说明用途，允许关闭麦克风并裁掉通知。录屏引用只留在内部分析，不进入参与者表单。
