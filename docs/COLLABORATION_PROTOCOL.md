# Alan × Codex 协作协议

> 目的：让 Alan 保持创作判断力，不被实现细节拖住；让 Codex 对方案、实现、验证和收尾负责。本文约束后续协作方式，不改变已经确认的游戏设计。

## 一、当前判断

目前的分工方向基本正确：Alan 最有价值的输入是感觉、方向、边界与取舍，而不是替 Codex 补齐所有设计和实现细节。

现有流程的问题不是 Alan 参与太少，而是讨论中的即时想法有时过快变成规格或生产任务。仓库已有几次明显信号：四季机制在单季验证前一次性铺开、视觉路线多轮切换、试玩记录形式返工。这些不说明创作判断有问题，而说明流程缺少“候选 → 原型 → 验证 → 承诺”的缓冲层。

因此，今后默认采用：**Alan 定义体验与取舍，Codex 提出并执行可验证方案；先看结果，再讨论细节。**

## 二、职责边界

### Alan 负责

- 描述希望玩家产生的感觉，例如“冬天应该孤独但不绝望”；
- 指出不喜欢、违和或失去灵魂的地方，不必先解释技术原因；
- 给出不可丢失的原则、禁区、参考物和优先级；
- 在真正影响产品方向的 2～3 个方案中做取舍；
- 对可玩的构建、截图、声音或玩家反馈做最终审美与产品判断。

### Codex 负责

- 把模糊感觉翻译成设计假设、实现方案与验收标准；
- 主动查代码、文档、依赖与历史决策，避免让 Alan 重复提供已有信息；
- 先给推荐方案，必要时只呈现少量具有实质差异的备选；
- 承担交互、数值、架构、边界情况、测试、文档、分支和 PR 收尾；
- 区分事实、推断、审美建议、AI 模拟与真实玩家证据；
- 发现方向不成立时主动停下，不用沉没成本绑架决策。

### 不应要求 Alan 负责

- 逐项指定控件位置、数值、代码结构、文件名或实现步骤；
- 在没有原型或对比材料时凭空回答大量细节问题；
- 替 Codex 检查遗漏、保持文档一致性或设计测试方法；
- 对可逆的小决定逐一批准。

## 三、想法的四级状态

所有新想法默认处于第一级，除非 Alan 明确说“就这么定”或“直接实现”。

1. **感觉**：主观反应或方向，例如“现在太像工具，不像一个世界”。不进入排期。
2. **候选**：Codex 将感觉翻译成 1 个推荐解法，必要时附 1～2 个备选和代价。不进入正式生产。
3. **实验**：用最小原型、截图、短音频、数值模拟或一小段可玩切片验证一个问题。允许丢弃。
4. **承诺**：通过 Alan 或外部玩家验证后，才写入正式计划并扩展到完整内容。

任何大面积内容生产、美术批量制作、系统级重构，都必须经过“实验”再进入“承诺”。

## 四、一次高效任务的默认流程

### 1. Alan 给方向

最短可以只说三件事：

```text
我想要：玩家在冬天感到彼此依赖。
我不要：苦难叙事、说明文字、强制正确答案。
我会用什么判断：玩完后是否自然想靠近蜂群。
```

不清楚的部分可以空着。Codex 应从仓库和已有共识中补齐背景。

### 2. Codex 回述与立约

开始实现前，Codex应简短说明：

- 我理解的目标；
- 我准备验证的核心假设；
- 本轮明确不做什么；
- 完成后 Alan 将看到什么证据。

只有目标存在实质歧义、不同答案会造成昂贵且不可逆的分叉时，才向 Alan 追问。

### 3. Codex 自主完成细节

可逆的实现细节由 Codex 直接决定。遇到重要分叉时，应给出推荐项与取舍，不把开放式设计作业退回给 Alan。

### 4. 用产物评审，不用抽象争论

优先评审顺序：可玩构建 > 动态画面/声音 > 静态对比 > 文字方案。Alan 可以只反馈“更像 / 更不像”“哪里脏”“哪里失去味道”，Codex 负责诊断原因并迭代。

### 5. 验证后归档

只有稳定结论进入设计共识、计划或 ADR。被否决的实验保留简短结论，避免以后重复踩坑；不把每次聊天都扩写成永久规格。

## 五、何时必须让 Alan 决策

Codex 只在以下情况暂停并请求选择：

- 改变核心幻想、目标玩家、商业定位或主题表达；
- 同时影响多个系统，预计返工成本明显；
- 会删除、覆盖或公开发布重要内容；
- 两个方案都成立，但代表不同审美或价值取向；
- 外部玩家证据与 Alan 的创作直觉冲突。

其余情况默认自主推进，并在交付时说明决定与依据。

## 六、防止“做成一坨”的门禁

- **一轮只验证一个核心问题**，不要同时改玩法、美术、音乐和叙事；
- **先做代表性切片**，不在方向未证实时批量生产；
- **设置停止条件**：若原型没有让目标感受更清晰，先诊断或撤回，不继续加内容；
- **限制选项**：默认一个推荐方案，最多两个真正不同的备选；
- **真人证据分层**：Alan 的实机反馈是真实的创作者／产品负责人玩家证据，优先用于方向和取舍；未参与开发的外部试玩用于检验陌生人理解和市场外推。AI 推演和开发者自测不能代替任一层；
- **方向与完成度分开评审**：先问“是不是我们要的”，再问“做得够不够精”。

## 七、任务拆分、分支、worktree 与集成

一次任务开始前，Codex 先判断它能否被独立验收，而不是按“玩法 / 美术 / 音乐”这些宽泛名词机械拆分。

### 可以并行的条件

- 子任务有各自清楚的玩家问题、范围和验收证据；
- 一个子任务的结论不会改变另一个子任务的前提；
- 不需要多个分支同时修改同一核心文件或同一段设计共识；
- 失败时可以单独撤回，不会留下半套玩家规则。

音乐盲听、外部试玩、Windows 验证、只读审计和独立资产实验通常可以并行。关卡数值、Boss 规则、季节路线等若依赖同一轮试玩结论，应先取得证据再排实现。

### 必须保持为一条任务链的情况

- “世界事实 → 玩家操作 → 成功判定 → 教学演示 → 回归测试”属于同一个因果链；
- 多个改动共同决定一个玩家能否理解或完成的动作；
- 多个分支需要同时编辑 `main.gd`、共享数据表、总流程测试或当前共识文档；
- 后一项只有在前一项被 Alan 接受或被玩家证实后才有意义。

急转的锁线、输入、成功证据、老师傅示范和两轮练习就是一条不可拆散的任务链。可以让子任务并行做只读诊断、测试设计和评审，但同一文件只有一个编辑责任人，最后由一个集成分支收口。

### 默认 Git 结构

- **一个独立问题 = 一个 branch + 一个 worktree + 一个 PR + 一组验收证据**；
- 分支从最近一次已接受且 CI 通过的基线创建。若前置 PR 尚未合并，默认先完成前置验收和合并，不制造不透明的叠层分支；
- 确需叠层时，PR 必须写明父分支、依赖、合并顺序，并在父 PR 合并后重新基于 `main`；
- 合并顺序按依赖关系，不按谁先写完；每次集成后重新运行自动检查和必要的人工流程；
- 不让多个并行分支同时维护 `PROJECT_LOG.md` 或整改总计划。各分支先保存自己的证据，由最后的集成任务统一更新总账。

每个子任务的交接信息至少包括：目标、明确不做、依赖、负责分支与 worktree、可见验收条件、已运行检查、仍需谁来验证。

### 环境与进度门禁

- 每次启动 Godot、构建或交付前，必须核对并报告绝对 worktree 路径、分支、短提交号和对应 PR；不能只说“最新版”；
- 一个 worktree 只能代表它当前检出的分支。另一个目录打开后看到旧版，不得误判为提交未生效；
- 执行中若超过约 60 秒没有可见结果，Codex 应主动报告正在做什么、已经得到什么、是否仍在运行；
- 工具报错、prompt flag、子任务失败或等待超时都不是交付。发生后必须明确说“任务未完成 / 哪部分已完成 / 下一步如何恢复”；
- 最终交付统一给出：**已完成、未完成、证据、正确打开方式、下一步决策**。不能用一串日志或工具输出代替状态结论。

## 八、默认沟通约定

- Alan 的“感觉不对”视为有效问题报告，不要求先给解决方案；
- Alan 的灵感默认是候选，不等于排期；
- Codex 不因一句随口建议就扩大范围；
- Codex 的推荐必须包含代价和验证方式，但不堆砌过程细节；
- 每次交付先说结果、风险与待验证项，再给文件和技术信息；
- 若 Alan 说“你决定”，Codex 应真正做决定并承担验证，而不是继续追问偏好。

## 九、近期适用方式

当前项目已有 Alan 的多轮真实实机反馈；最大的流程问题是可玩候选交付不够快，最大的证据缺口才是独立新玩家体验。近期协作应优先采用：

1. Codex 把一个明确问题做成可玩的最小切片；
2. Alan 只做一次方向审阅，避免像素级共同设计；
3. 尽快交给外部玩家；
4. Codex 汇总证据并提出下一步推荐；
5. Alan 只对是否继续、转向或放弃作产品判断。

这使 Alan 更像导演与产品负责人，Codex 更像拥有执行责任的设计/工程团队，而不是两个人同时握着同一支笔修改每个像素。

## 十、单一执行视图与在制品限制

2026-08-28 的[流程效率审计](PROCESS_EFFICIENCY_REVIEW_2026-08-28.md)确认：Alan 的验证速度快于候选交付速度；当前限制因素是实现批次、集成交付和优先级整合，不是 Alan 参与不足。后续增加以下默认规则：

- 每轮只指定一个活跃执行视图；其它规格、日志和历史清单不得同时充当待办队列；
- 同时最多保留一个核心学习目标、三个 `Now` 项和一条实现主链；可以另开一条不改变主链前提的只读审计、设备验证或外部测试；
- 同一玩家问题的实现、测试、可见证据和事实更新放在同一 PR，不把连续修补和文档同步拆成多个无需独立验收的即时 PR；
- 在 Alan 或目标玩家验证代表切片前，不从“实验”升级到批量内容生产；自动回归只能排雷，不能触发扩产；
- 每个 `Now` 项必须写明可证伪假设、停止条件和所需证据。没有证据时默认停止或继续验证，不以已写代码量推动承诺；
- README 只保留当前摘要和事实源入口；规格维护规则，执行视图维护状态，日志保留历史。瞬时分支、dirty tree 和 PR 候选状态不写入稳定共识长期维护。

当前近期门禁是：先从最新主线收口 HUD／输入合同并尽快生成 clean 候选，完成 Alan 对立春—谷雨代表流程的定向试玩。Alan 接受代表切片后可以继续下一有限切片；其余 330 条事件的批量生产与下一款游戏生产，要等首批独立玩家第一小时证据支持后再启动。

## 十一、风险分级验证

- 文档纯改动至少运行 `git diff --check`，可走轻量 CI；
- 普通代码改动运行定向测试，并由完整 CI 关闭 Web、Godot 与导出边界；
- 存档、输入、发布、artifact 身份和试玩证据链属于高风险改动，除完整 CI 外还需从用户路径反读一次 diff，并取得对应人工流程证据；
- CI workflow 或轻量分类器自身发生变化时，不能只以“轻量 gate 通过”证明完整路径有效；合并前应显式取得一次完整运行证据；
- 在仓库无法强制 branch protection 时，保留 `main` push 后的质量复跑。先通过减少碎片 PR、缓存依赖和避免重复构建降本，再评估取消安全复跑。

## 十二、有依据的设计与商业讨论

2026-08-31，Alan 明确要求不要用非此即彼和泛泛概念反复讨论，指定参照[协作规范](https://alanthssss.github.io/collaboration/)。本节据其[原则](https://github.com/alanthssss/collaboration/blob/3354b9eeb879818089be66cfd7f1a0551f6a1b15/docs/principles.md)、[实践](https://github.com/alanthssss/collaboration/blob/3354b9eeb879818089be66cfd7f1a0551f6a1b15/docs/practices.md)与讨论／决策模板补充项目约束；链接版本用于追溯，不自动把网页日后的修改当作本项目决定。

- **先确定实际问题。** 例如“怎样让 360 项内容轻松且可生产”，不偷换成“要轻量还是要内容”。分别列出体验、功能、内容量、制作资源、时间与商业约束；缺少预算就写未知，不假定小团队只能做短篇。
- **区分五类表述。** 事实给可核查来源；判断解释推导；假设写未知与反证；建议写机制、收益、成本和替代办法；决定注明 Alan 已确认的具体边界。外部案例、静态代码、开发者自测、Alan 实玩和独立玩家证据分别标记，不互相代签。
- **不制造互斥。** 先比较能调整的维度和可共用的规则。只有资源约束、逻辑关系或用户明确禁区使两项不能同时成立时，才提出二选一，并把这个条件写明。少给选项是减少噪声，不是禁止组合。
- **重要建议落到具体事件。** 至少说明玩家做什么、为何产生预期体验、系统需要增加什么、什么现象说明没奏效。若只是示意案例，要标未实现；不得将文案中的结果当成运行时事实。
- **按证据尺度下结论。** 两条故事可以初测复用，不能证明全年成本和长期乐趣；少量访谈用于发现问题，不能证明销量。数值应标来源、假设或纯算例，不能把方便记录的阈值写成行业真理。
- **以收敛记录结束。** 明确本轮确认、撤回、仍分歧／未知，以及下一步可改变结论的证据。需行动时写责任人、完成条件和日期；尚未授权或依赖招募时明确未排期，不捏造承诺。不要求 Alan 为已有材料可以回答的问题重复作答。
- **新反馈不自动重写旧决定。** 当“轻量”等词存在多维解释时，先检验具体机制与约束；改变内容目标、类型或商业范围仍需明确决定。发现 Codex 推断越界时同步修正事实源与引用，保留简短撤回理由，而非只新增相反段落。

本节约束讨论质量，不新增重复表单或独立计划；使用已有商业要求、专项规格和日志承载相应结果。对简单问题可用短段落完成上述区分，不机械套长报告。
