# 数值设计总览 / Numeric Design Compendium

> 状态：**当前代码／数据事实快照；调参结论仍待真人数据**。本文汇总关键数值、设置依据、交互与反馈设计，不冒充唯一实现源。
> 当前数值分布在 `godot/data/*.json` **和脚本常量／状态机**。外部数据项改 JSON 后重启生效；脚本所有的移动、窗口、阶段与表现参数必须在相应 `.gd` 与测试中修改。本文与代码不一致时，**以代码／数据为准并在同一任务修本文**。
>
> 相关文档：难度调优框架见 `docs/DESIGN_CONSENSUS.md` 与 `docs/PROJECT_LOG.md`；推演工具 `scripts/difficulty_table.py`。

## 0. 设计总则（为什么数值是这样组织的）

1. **数据优先，不是 JSON 唯一入口**：主要可配平衡数值位于 `godot/data/`（`balance.json` / `seasons.json` / `upgrades.json` / `bosses.json` / `flowers.json`）；状态机、移动手感、阶段窗口和部分表现仍由脚本常量控制。先确认参数的真实所有者，不得修改 fallback 来绕过正式数据源。
2. **一条核心张力驱动全部数值**：「再采一朵，还是现在归巢？」（One more flower, or home now?）。体力（energy）、蜜囊容量（carry capacity）、节气目标（goal）三方互相约束，每个数值都在调节这三者的夹角。
3. **难度曲线用"成本"而非"惩罚"表达**：后期不是"敌人更多所以更难"，而是每滴蜜的体力成本、时间成本、风险成本同时上升（drain↑ / scale↓ / 敌人构成变化）。
4. **守恒而非没收**：失败/被偷的蜜以"返蜜花"回归花田（nectar conservation），损失是延迟不是删除——这是生态叙事的一部分，也是数值上"永远有解"的保证。

| 采蜜耗能 harvest_energy_per_second | 3.2 /s | balance.json | 采蜜比飞行贵（基础 drain 1.25~2.3），悬停采蜜是最危险的状态 |

| 急转 evade | 锁线后同方向 0.34s 内连按两次，记录第一次输入位置并沿该方向以 520px/s 侧掠 0.18s；耗 12 体力，无伤 0.18s（`player.evade_invuln_seconds`），冷却 1.6s | main.gd + bee_player.gd + balance.json | 锁线攻击的空间解法：从锁定位置附近开始、离开危险通道；无伤时间仅保护动作过渡，不再充当教学成功证据 |
| 受击无敌间隔 hit_cooldown | 0.9s（被击中后的短无敌窗） | balance.json | 批次2 落地：1.05→0.9s + 移出硬编码，连击威胁更高 |
| 蚊虫嗅觉 sense_range + sense_per_carry | 330px + 每滴携带蜜 +12px（满载 8 滴 = 426px） | balance.json | 蜜香招敌（批次2 落地）：满载显眼，"再采一朵"的代价从体力扩展到暴露 |
| 力竭进度惩罚 exhaustion_delivered_penalty | 已入库进度回退 2 滴（以返蜜花回到花田，守恒不破） | balance.json | 批次2 落地：力竭不只扣命，本关进度也受损——归巢止损更有分量 |
| 入巢卸蜜延迟 hive_deposit_delay | 0.4s（站稳才卸蜜，离巢清零计时） | balance.json | 批次2 落地：归巢是停靠决策，不是贴边擦存；防蹭巢速存速撤 |
| 归巢恢复 hive_rest_per_second | 20/s（冬季减半） | balance.json | 回巢停留≈5s 回满（冬季 10s），"归巢"本身是一个恢复决策 |
| 饮蜜 drink_honey（E 键） | +22 体力（加法+钳制到上限），每节气限 2 次 | balance.json | 显式饮蜜（PR #44/#45）：蜜囊里的蜜可以做"续力"还是"交付"的资源抉择；上限防止饮蜜替代归巢 |
| 力竭宽限 exhaustion_beat_seconds | 1.1s | balance.json | 体力见底不是立刻死，有最后一搏窗口（归巢/饮蜜）；期间不自动吃蜜（显式化决策） |
| 失败重开体力 post_failure_energy | 45 | balance.json | 重试不是满状态白给，但也不至于开局即死 |
| 蜜囊容量 carry_capacity | 固定 8 滴 | balance.json | 容量 8 vs 普通目标 10~15：每关至少 2 趟；成长不再扩大容量，避免后期重新退化成一次归巢 |

**体力经济学示例**（不带升级，不含采蜜耗能）：

- `100 / 1.25 ≈ 80s`、`100 / 2.0 = 50s`、`100 / 2.3 ≈ 43s` 分别是只扣基础 `drain_rate` 的理论上限，可用来比较节点压力，但不能标成“满速出勤”。
- 持续移动超过 `0.35s` 且体力 `> 8` 时会自动冲刺，实时消耗率为 `drain_rate + 9.5 × dash_cost_multiplier`。默认倍率为 `1.0`；每次长翼成长会再乘 `0.85`。
- 以首节点默认数值为例，自动冲刺阶段每秒约消耗 `1.25 + 9.5 = 10.75`；因此 80s 只是不含冲刺附加项的基础比较值。真实单趟还要叠加采蜜、急转、惊退、环境减速和玩家停留，必须用节点实测而不是一个除法代替。

## 2. 花蜜产出公式（难度的心脏）

```gdscript
nectar_val = max(2, roundi(base_nectar * nectar_scale)) + extra_nectar
# base_nectar 来自 flowers.json 按季节花型权重抽取
# extra_nectar = 采蜜蜂升级每级 +1
```

| 要素 | 值 | 依据 |
|---|---|---|
| min-2 钳制 | 单花基础结果至少 2 滴 | 当前 `nectar_scale` 全范围为 0.7～1.24；`max(2, ...)` 保证缩放后的基础结果不降到 1，但花型、花数与机制成本仍会改变节点供给 |
| nectar_scale | 冬 1.1 → 夏峰 1.24 → 深冬 0.7 | 与"被需要的四季"同步：春花渐丰、夏顶点、秋冬递减 |
| 花型权重 flowers.json | 春（3/2/2 混合+连锁）、夏（5 滴 peak 占 50%、7 滴 cascade 20%）、秋（1 滴 seed~4 滴 late 混合）、冬（hidden/warmth/frozen） | 物候学表达：夏季是"单朵丰收"，秋冬是"单朵贫瘠但结构多样" |
| 目标 / 花数范围 | 普通目标 10～15；花数 6～8 | 目标始终高于蜜囊容量 8；路线机制与永久消耗另设资源预算，不再依赖最低随机产量碰巧可解 |

**测试约束地板**（改动前必跑，`godot/tests/`）：

- flow_test：每个普通目标必须大于固定 8 滴容量；
- flow_test：初始可回收花蜜必须覆盖目标、每关 2 次合法饮蜜，以及留种／暖点的最大永久消耗；
- season_mechanics_test：冬季必须完成 3 个暖点，夏季必须逐只惊退实体袭扰者。

**关键节点当前配置**：

| 内部节点 | 目标 | 花数 | 主行为 |
|---|---:|---:|---|
| 冬至 | 11 | 6 | 因果教学 + 完成 2 次同型花传粉 |
| 谷雨 | 13 | 7 | 真实卸蜜触发袭扰 |
| 立夏 | 14 | 7 | 拦截实体劫掠路线 |
| 芒种 | 15 | 6 | 夏段最高交付目标 |
| 白露 | 14 | 8 | 留最后一滴或采尽的后果 |
| 大雪 | 11 | 7 | 三暖点完整接力 |

花蜜总量由花型随机和采蜜蜂等级共同决定，因此不再把单次抽样均值写成固定事实；可解性由运行时资源预算与测试门禁保证。

| Boss | 节点 | 速度 | 伤害 | 调律半径 | 主题 |
|---|---|---|---|---|---|
| 失律之蚊 | 春分 | 78（轨道） | 体力 18 / 蜜 1 | 82 | 贪婪·持续索取 |

## 7. 交互清单（玩家能做什么）

| 输入 | 动作 | 数值锚点 |
|---|---|---|
| WASD/方向 | 飞行（加速/惯性/制动模型） | 215 / 冲刺 360 / 闪避 520 |

| 空格/回车（情境） | 近敌→惊退；静止→摇摆舞寻迹；近花→按住采蜜 | 优先级：惊退 > 寻迹 |
| 松开情境键后长按 | 投蜜诱饵（decoy） | 耗 1 滴蜜，蚊改追诱饵；结束后蜜回到花田 |
| Q | 归巢路线锁定（自动飞回） | 归巢是显式决策 |
| E | 饮蜜续力 | +22 体力，限 2 次/节气 |
| 蜂巢内停留 | 体力恢复 + 储蜜/征召/抱团机制 | 20/s（冬 ×0.5） |

## 8. 反馈清单（游戏如何回应玩家）

**通道 1 · 文案（message，HUD 侧栏单条事件文案）**

每个游戏事件对应一条叙事化文案，如：
- 受击：「蚊虫刺中了你：体力下降，花蜜洒落。」
- 归巢：「安全归巢，存入 N 滴蜜。蜂群的照料正在恢复体力。」
- 力竭：「翅膀停在了半空。携带的 N 滴蜜将洒落花田，蜂巢的呼吸弱了一分……」
- 饮蜜三条固定文案：空囊「蜜囊已经空了。」/ 限尽「这趟出勤，蜜囊续力已到尽头。」/ 饮下「你饮下蜜囊里的一滴蜜，翅膀重新有了力气。」

依据：文案即叙事载体（"蜂巢的呼吸"=群体存亡），不用系统口吻。采蜜成功文案已在 PR #43 删除——高频事件不配文案，防刷屏。

**通道 2 · 视觉瞬时反馈**

| 事件 | 反馈 | 参数 |
|---|---|---|
| 受击（蚊/油葫芦/熊/Boss） | 屏幕闪光 | flash 0.4~0.55，受击越重越亮 |
| 饮蜜 | 轻闪光 + 能量条闪 | flash 0.28 / 能量条闪 0.8s |
| 蜜囊已满仍采 | 携带条红色脉冲 + 闷音（PR #43） | 0.6s、24Hz 脉冲 |
| 归巢交蜜 | 蜂巢区闪光 | hive_flash 1.0s |
| 采蜜 | 每滴音效 + 能量增减浮字（`%+d`） | — |
| 闪避/惊退/升级/调律/胜负 | 各自专属音效 cue | 见下 |

**通道 3 · 音效（程序化生成，sound_feedback.gd，ADR-002）**

cue 清单：harvest / full / repel / evade / attack_lock / evade_clear / hurt / home / drink / loss / upgrade / tune / win / decoy。`evade` 只确认动作发动，`attack_lock` 确认路线提交，`evade_clear` 才确认敌害穿过旧位置且蜜蜂离线。
背景音乐为 8 个独立 WAV：春、夏、秋、冬各 1 首探索主题和 1 首 Boss 变奏。旧单一程序化背景循环、常驻低频 pad 与 Boss 全局降调已移除；当前路由由 `music_director.gd` 管理。资源差异与循环已通过开发者自测，听感仍待真人盲听和实机 A/B。

**通道 4 · 状态常显（HUD）**

体力条（含上限变化）、「携带 X/上限」「归巢蜜 Y/目标」；普通关侧栏常驻归巢蜜、季节机制与老师傅当前要求，Boss 战显示「调律 N/3」。

**为什么这么做**：四通道分工——文案管叙事（低频、事件级）、闪光/音效管即时确认（高频、感官级）、HUD 管持续决策依据。反馈不解释规则（非说教），而是让玩家从"蜜洒落→返蜜花"这类因果链里自己读出系统。

## 9. 调参工作流

1. 先定位参数所有者：可配节点／玩家／Boss／花／成长数值改 `godot/data/*.json`；状态机、移动手感、时间窗和表现常量改对应 `.gd`，并同步测试。禁止改 fallback 值绕过正式数据源。
2. 节点资源参数改动前跑 `python3 scripts/difficulty_table.py table`，改后跑 `validate <seasons.json>`；脚本常量改动则补充或更新直接覆盖该行为的测试。
