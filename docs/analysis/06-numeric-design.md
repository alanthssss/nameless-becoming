# 数值设计总览 / Numeric Design Compendium

> 状态：**已定稿（对应代码现状）**。本文是项目数值的唯一集合参考，汇总当前所有关键数值、设置依据、交互与反馈设计及其理由。
> 数据源以 `godot/data/*.json` 与脚本常量为准；调参只改 JSON（无热重载，改完重启）。本文与代码不一致时，**以代码为准并回来修本文**。
>
> 相关文档：难度调优框架见 `docs/DESIGN_CONSENSUS.md` 与 `docs/PROJECT_LOG.md`；推演工具 `scripts/difficulty_table.py`。

## 0. 设计总则（为什么数值是这样组织的）

1. **数据驱动（data-driven）**：所有可调数值外置到 `godot/data/`（`balance.json` / `seasons.json` / `upgrades.json` / `bosses.json` / `flowers.json`），代码零硬编码可调项，单配置文件，改 JSON + 重启即生效（2026-08 alan 拍板，明确不做热重载）。
2. **一条核心张力驱动全部数值**：「再采一朵，还是现在归巢？」（One more flower, or home now?）。体力（energy）、蜜囊容量（carry capacity）、节气目标（goal）三方互相约束，每个数值都在调节这三者的夹角。
3. **难度曲线用"成本"而非"惩罚"表达**：后期不是"敌人更多所以更难"，而是每滴蜜的体力成本、时间成本、风险成本同时上升（drain↑ / scale↓ / 敌人构成变化）。
4. **守恒而非没收**：失败/被偷的蜜以"返蜜花"回归花田（nectar conservation），损失是延迟不是删除——这是生态叙事的一部分，也是数值上"永远有解"的保证。

## 1. 玩家核心数值（balance.json `player` 段 + bee_player.gd）

| 数值 | 当前值 | 出处 | 设置依据 |
|---|---|---|---|
| 体力上限 max_energy | 100 | balance.json | 基准量尺，所有恢复/消耗以它为 100% 口径 |
| 体力自然流失 drain_rate | 1.25 → 2.3 /s（按节气） | seasons.json `energy_drain` | 主难度旋钮。满体力纯飞行窗口从冬至约 80s 压缩到深冬约 43s，迫使后期"多趟归巢" |
| 自动冲刺 auto-dash | 持续移动 >0.35s 触发，速度 360（基础 215） | bee_player.gd 常量 | 速度即消耗选择：快飞多耗（额外 9.5×dash_cost_multiplier /s），需要 >8 体力 |
| 移动手感 | 加速 1050 / 制动 1280 | bee_player.gd 常量 | 惯性飞行手感（加速/惯性/制动模型），非硬切速度 |
| 采蜜间隔 harvest_interval | 0.42 s/滴 | balance.json | 一滴蜜约 0.4s 站桩，配合敌袭构成"采蜜被打断"的风险窗口 |
| 采蜜耗能 harvest_energy_per_second | 3.2 /s | balance.json | 采蜜比飞行贵（基础 drain 1.25~2.3），悬停采蜜是最危险的状态 |
| 惊退 repel | 耗 8 体力，范围 88px，冷却 1.15s，持续 3.5s | balance.json | 防身技但有代价；冷却防止无脑清场（批次2 计划持续 3.5→1.8s） |
| 闪避 evade | 双击方向触发，耗 12 体力，冲刺 520px/s，无敌 0.34s，冷却 1.6s | bee_player.gd | 高级防御：操作换生存（批次2 计划无敌 0.34→0.18s） |
| 归巢恢复 hive_rest_per_second | 20/s（冬季减半） | balance.json | 回巢停留≈5s 回满（冬季 10s），"归巢"本身是一个恢复决策 |
| 饮蜜 drink_honey（E 键） | +22 体力（加法+钳制到上限），每节气限 2 次 | balance.json | 显式饮蜜（PR #44/#45）：蜜囊里的蜜可以做"续力"还是"交付"的资源抉择；上限防止饮蜜替代归巢 |
| 力竭宽限 exhaustion_beat_seconds | 1.1s | balance.json | 体力见底不是立刻死，有最后一搏窗口（归巢/饮蜜）；期间不自动吃蜜（显式化决策） |
| 失败重开体力 post_failure_energy | 45 | balance.json | 重试不是满状态白给，但也不至于开局即死 |
| 蜜囊容量 carry_capacity | 基础 8 滴 | balance.json | 容量 8 vs 目标 9~12：一关至少 2 趟，"归巢"被机制强制成运力决策（PR #41） |

**体力经济学示例**（不带升级，不含采蜜耗能）：

- 冬至：100 / 1.25 ≈ **80s** 满速出勤窗口 → 单趟从容，教学定位
- 处暑：100 / 2.0 = **50s** → 必须规划路线
- 大雪：100 / 2.3 ≈ **43s**，且冬季恢复减半 → 归巢节奏成为核心玩法

## 2. 花蜜产出公式（难度的心脏）

```gdscript
nectar_val = max(2, roundi(base_nectar * nectar_scale)) + extra_nectar
# base_nectar 来自 flowers.json 按季节花型权重抽取
# extra_nectar = 采蜜蜂升级每级 +1
```

| 要素 | 值 | 依据 |
|---|---|---|
| min-2 钳制 | 单花至少 2 滴 | 0.85~1.1 的 scale 区间内冬节令单花量恒定（约 2.0~2.45），**冬季稀缺只能靠减花数表达**，不会出现"1 滴花"的挫败感 |
| nectar_scale | 冬 1.1 → 夏峰 1.24 → 深冬 0.7 | 与"被需要的四季"同步：春花渐丰、夏顶点、秋冬递减 |
| 花型权重 flowers.json | 春（3/2/2 混合+连锁）、夏（5 滴 peak 占 50%、7 滴 cascade 20%）、秋（1 滴 seed~4 滴 late 混合）、冬（hidden/warmth/frozen） | 物候学表达：夏季是"单朵丰收"，秋冬是"单朵贫瘠但结构多样" |
| 目标/花数比 goal/flowers | 冬至 5/6=0.83 → 处暑 12/6=2.0 | 后期必须采尽几乎全部花（或依赖授粉新增花），逼玩家用满整个花田 |

**两条测试约束地板**（改动前必跑，`godot/tests/`）：

- flow_test：最坏情形 花数×2 ≥ 目标（处暑/白露 6×2=12=目标 已是边界，**不可再减花**）
- smoke_test：花数×maxi(2, roundi(3×scale)) ≥ 目标

**关键节令实际数值**（`difficulty_table.py table` 实测，main）：

| 节令 | 目标 | 花数 | 单花均值 | 总蜜 | 倍数(总蜜/目标) | 蚊/蚁/蟋/熊 |
|---|---|---|---|---|---|---|
| 冬至 | 5 | 6 | 2.45 | 14.7 | 2.94 | 0/0/0/0 |
| 谷雨 | 9 | 7 | 2.80 | 19.6 | 2.18 | 3/1/0/0 |
| 立夏 | 10 | 7 | 6.00 | 42.0 | 4.20 | 3/1/0/0（夏花丰收期） |
| 芒种 | 11 | 6 | 5.80 | 34.8 | 3.16 | 4/1/1/0 |
| 白露 | 12 | 6 | 2.50 | 15.0 | **1.25** | 3/1/2/1（最紧：几乎零容错） |
| 大雪 | 8 | 5 | 2.00 | 10.0 | 1.25 | 0/0/0/0（无敌人但蜜极少） |

> 倍数 <1.4 的节令（处暑/白露/寒露/立冬/小雪/大雪）是难度顶点：敌人还在但蜜不再充裕——"匮乏"由数据结构表达而非文案。

## 3. 成长三选一（upgrades.json，可叠加，UPGRADE_CAP=6）

| 卡牌 | 数值 | 设计意图 |
|---|---|---|
| 长翼蜂·疾 | 速度 +10%、冲刺耗能 -15%（每级乘法叠加） | 效率型：同一体力飞更远 |
| 采蜜蜂·蜜 | 采蜜间隔 -15%、每朵花额外保留 1 滴、容量 +3 | 运力型：容量 8→26（满级），配合多趟策略 |
| 守卫蜂·守 | 惊退范围 +18%、震翼冷却 -15% | 生存型：高压段的容错 |

依据：三张卡分别优化"时间成本/运力成本/风险成本"——正好对应核心张力的三个变量，构筑方向即玩家对难度的回答。数值取中等百分比（10~18%），保证单级有感、满级不破版。

## 4. 敌人数值（balance.json 各段）

| 敌人 | 关键数值 | 设计意图 |
|---|---|---|
| 蚊 mosquito | 感知 330px、速度 65、体力伤 10、蜜伤 1 | 慢于玩家（215）但感知范围大：花田里的"压力常数"，逼玩家动起来 |
| 蚁 ant | 速度 58、偷蜜 1 滴、受惊逃离 1.4s | 不伤人只偷蜜→经济敌人；被惊退会丢蜜（守恒回归） |

| 画眉 thrush | 每 8s 唱歌、幻花半径 120、最多 3 朵、34px 内揭示 | 信息敌人：用假目标污染玩家的花田决策 |
| 熊 bear | 速度 30、压平半径 30、9s 压平一朵花、接触伤 16、吃蜜间隔 4s | 不可惊退（震翼无效，需绕开）：唯一"不可解"敌人，制造纯规避压力 |
| Boss 失律者 | 见 bosses.json，调律 3 次制，无血条 | 见第 6 节 |

依据：敌人构成按节气曲线投放（seasons.json 各节令 mosquitoes/ants/crickets/thrushes/bears 字段），五种敌人分别攻击"体力/蜜/节奏/信息/空间"五个不同维度，避免难度只体现为"数值变大"。

| 输入 | 动作 | 数值锚点 |

## 8. 反馈清单（游戏如何回应玩家）

**通道 1 · 文案（message，HUD 侧栏单条事件文案）**

每个游戏事件对应一条叙事化文案，如：
- 受击：「蚊虫刺中了你：体力下降，花蜜洒落。」
- 归巢：「安全归巢，存入 N 滴蜜。蜂群的照料正在恢复体力。」
- 力竭：「翅膀停在了半空。携带的 N 滴蜜将洒落花田，蜂巢的呼吸弱了一分……」
- 饮蜜三条固定文案：空囊「蜜囊已经空了。」/ 限尽「这趟出勤，蜜囊续力已到尽头。」/ 饮下「你饮下蜜囊里的一滴蜜，翅膀重新有了力气。」

依据：文案即叙事载体（"蜂巢的呼吸"=群体存亡），不用系统口吻。采蜜成功文案已在 PR #43 删除——高频事件不配文案，防刷屏。

**通道 2 · 视觉瞬时反馈**

| 事件 | 反馈 | 参数 |
|---|---|---|
| 受击（蚊/油葫芦/熊/Boss） | 屏幕闪光 | flash 0.4~0.55，受击越重越亮 |
| 饮蜜 | 轻闪光 + 能量条闪 | flash 0.28 / 能量条闪 0.8s |
| 蜜囊已满仍采 | 携带条红色脉冲 + 闷音（PR #43） | 0.6s、24Hz 脉冲 |
| 归巢交蜜 | 蜂巢区闪光 | hive_flash 1.0s |
| 采蜜 | 每滴音效 + 能量增减浮字（`%+d`） | — |
| 闪避/惊退/升级/调律/胜负 | 各自专属音效 cue | 见下 |

**通道 3 · 音效（程序化生成，sound_feedback.gd，ADR-002）**

cue 清单：harvest / full / repel / evade / hurt / home / drink / loss / upgrade / tune / win / decoy。
背景音乐按四季换根音（A/B/G/E）、五声音阶（PENTATONIC）、五段式结构——**音乐是季节状态的 ambient 反馈**，不是装饰。

**通道 4 · 状态常显（HUD）**

体力条（含上限变化）、「携带 X/上限」「本关进度 Y/目标」、节气名+阴阳比、体温/储蜜（越冬段）、Boss 战「调律 N/3」。

**为什么这么做**：四通道分工——文案管叙事（低频、事件级）、闪光/音效管即时确认（高频、感官级）、HUD 管持续决策依据。反馈不解释规则（非说教），而是让玩家从"蜜洒落→返蜜花"这类因果链里自己读出系统。

## 9. 调参工作流（已定案）

1. 改 `godot/data/*.json`（唯一入口，禁止改代码内 fallback 值绕过）
2. 跑 `python3 scripts/difficulty_table.py table` 推演（改前）/ `validate <seasons.json>`（改后校验测试地板）
3. 跑 `godot/tests/` smoke_test + flow_test
4. 新增中文文案 → 先做字体子集缺字预检（`git show HEAD:<path>` 对比改动前字形集；当前缺字：付/袋/些/拒/产）
5. 重启游戏生效（无热重载）
