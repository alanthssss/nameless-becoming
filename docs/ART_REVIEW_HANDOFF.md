# 美术专家交接与自动化分享

状态：内部专家评审交接规范；不是美术批准或公开发行。

## 分享范围与阅读顺序

分享一个同时包含可运行游戏与材料的 ZIP，不要求专家安装 Godot、Node 或取得源码访问权。先解压并打开 `START_HERE.html`，核对版本／提交，再试玩、查看原图，最后填写 `FEEDBACK.md`。

1. **同提交游戏**：Windows x86_64 EXE 与 macOS universal ZIP；内嵌来源、实际文件 SHA-256 与包清单一致。版本号可能长期不变，必须同时引用完整提交号。
2. **运行候选原图**：商业导出白名单中的 21 张 PNG，不缩放、不重绘。图册显示尺寸、文件名、哈希，并可打开原图。包括四季背景、玩家／老师傅／工蜂、蜂巢、花、邻居、工作物与四张季末结果图。
3. **现行要求**：商业成品清单、Campaign 制作规格、剧情框架、美术来源登记、游戏信用／许可。它们分别描述目标、运行差距与来源，不能把待实现条目当作包内已实现。
4. **单独标记的参考**：现存六张 Journey 开发者截图与原始截图清单；概念主视觉、文字标、8 张商店尺寸候选及营销说明。历史截图不是本包 Campaign 同版本截图；概念主视觉不是玩法；产品名正在重评，品牌候选不是定稿。
5. **结构化反馈**：文件名或游戏内场景、实际看到的问题、截图／时间点、影响、严重度、修改建议、保留内容、预计工作量／依赖。专家判断单独归为 `[专家启发式]`，不计作独立玩家验收。

不附整个仓库、开发日志、存档、环境文件、令牌、第三方完整扫描书、旧测试入口、旧原型美术或历史毛毡／纸雕指导文件。文档中的本机用户目录将脱敏；不修改仓库原件。原图来源记录里的历史生成提示只用于审计，不覆盖现行风格要求。当前没有完整 PSD／分层源、完整动画和逐图授权链，不虚构交付。

## 评审问题

建议先用 20～30 分钟走通标题→主巢→立春出巢→实际交互→回巢接货，再看四季候选图。这是评审时间建议，不是游戏全长或通关承诺；不要为看后期画面要求专家先通关全年。

- 小尺寸与移动中能否辨认玩家方向、携带物、交互状态、路线和主巢入口？
- 角色、环境、工作物、UI 的线条、透视、明度、色彩、材质和比例是否统一？哪些必须重画，哪些能清稿沿用？
- 动作前兆、过程、成功／失败、负载、天气影响能否用画面说明，少依赖任务文字？
- 普通完整昆虫／鸟类身体、自然附着关系、温暖俏皮气质是否成立？有哪些解剖／透明边／图集切片问题？
- 四季和四场结果图是否有差异？结果图是否与实际玩法／角色一致？不要用漂亮插画替代运行表现评审。
- 下一步最值得制作的 3 个样板是什么？分别需要哪些分层源、动画状态、尺寸、命名、导出与验收标准？请给范围／依赖，不把估算当项目排期承诺。

专家无需替项目签署授权，也不能用评审通过替代 Alan 最终画风批准。所有候选保留 `AUTH-PENDING / ALAN-PENDING / PLAYER-PENDING / MKT-NO`。

## 本地一键打包

在干净、已提交的独立检出中，准备 Node 22.13+、Godot 4.6.2、官方 macOS／Windows 导出模板、`zip`／`unzip`；macOS 打包／ad-hoc 签名须在 macOS 上执行：

```bash
GODOT_BIN='/Applications/Godot 2.app/Contents/MacOS/Godot' npm run art:build
```

命令重跑 24 组 Godot 回归，再重建双端、签名 macOS、检查两份最终包的资源边界和内嵌来源，最后生成 ZIP。不得用环境变量把 dirty 工作树伪装成 clean；入口会独立检查 Git。不会读取或携带开发者个人存档。

已有**同一 HEAD** 的双端构建时，可仅重新整理材料：

```bash
GODOT_BIN='/Applications/Godot 2.app/Contents/MacOS/Godot' npm run art:package
```

它仍重新检查真正的游戏包，不盲信旧 manifest。默认输出 `outputs/art-review/` 下唯一的新目录；每次包含 ZIP 与 `.sha256`。可传 `--output /absolute/directory` 指定输出父目录，不覆盖既有分享包。包名含版本、UTC 日期、短 SHA 和随机后缀；`VERSION.json` 保存完整 SHA、时间、平台与声明边界；`MANIFEST.json` 保存除自身外所有文件的大小／SHA-256；ZIP sidecar 覆盖整个压缩包。构建后若改动源码、材料或提交，必须重新构建，不能继续标作原版本。

## 自动化分享机制

复用现有 **Desktop client builds**，增加依赖双端成功的 **Art expert review bundle** job；不建立另一套导出逻辑，也不另设定时任务。合并后每次桌面构建都会自动下载该次双端产物，按同一 `github.sha` 检出材料，复核内嵌来源，再上传一个完整专家 ZIP 和校验码。失败时不发布评审包。

在 Actions 页面选择 `main`、当前版本号、`publish_prerelease=false` 即可。也可从仓库执行：

```bash
gh workflow run desktop-build.yml --ref main -f release_tag=v0.9.5-rc.2 -f publish_prerelease=false
```

版本变化后同步参数；不要把此示例版本永久写死在外部系统。每次成功运行的 Summary 提供该次不可混版的 artifact 下载链接，保留 30 天；不要用“latest”指代没有固定身份的游戏。Actions 外层下载包中才是可直接转发的专家 ZIP 与 sidecar。

**访问边界**：目前仓库私有，Actions 链接需要有仓库读取权限的 GitHub 账号；它不是任何人可访问的网盘链接。无仓库权限的外部专家，由 Alan 下载 ZIP 后通过双方认可的私聊／受限网盘发送；不得仅为取包给专家整库权限。这里自动化的是构建→校验→汇总→受限下载链接，不会自动发送邮件、加协作者、创建公开 release 或修改网盘权限。自动发送到指定联系人／网盘需要先提供接收目标与访问范围，再接入；不把凭证写进仓库或资料包。

macOS 候选仅 ad-hoc 签名且未公证；Windows 未做发行签名，可能被系统拦截。提醒专家只运行来自可信发送者且核对哈希的包，不要求关闭全局安全防护。自动回归、导出检查和专家启发式都不等于 Windows 真机、完整玩法、授权或商业发行验收。无头检查不证明实际画面／声音正确。
