# 《雨来之前》开发范式：稳定元素，再组合完整体验

版本：1.0，2026-10-28。依据：Alan要求形成阶段、目标、流程、规范和门禁，供后续继续工作。Codex负责实施、内部检查和交接；Alan负责整体审美、产品方向及真正的范围／成本取舍。

本文是当前项目的生产规则。按Alan于2026-10-28要求，GitHub milestone／issue管理目标、依赖和结果；**当前阶段、选中的issue和唯一下一动作只维护在[制作规格§0.11 Now](solar-term-campaign-production-spec.md#production-now)**，具体版本与门禁证据留在原批次回执。本文只索引路线，不复制一套动态待办。历史实现不因本规范建立而自动通过任何门禁。

**对用户的交付名称（2026-11-01）。** 当前整段称为“池岸归途”：从池边出发，选路穿雨、帮助邻居，最后回到蜂巢。汇报以实际可玩的旅程和完整24关发布缺口为单位，不再用内部关卡编号作概念。代码、旧包与历史记录中的编号仅供定位，不改变其映射。

## 1. 不随工作段变化的约束

- **完整产品目标是24关。** 旧GDD的20关及24物候合并表不能视为满足要求；四季各六关，以及池岸归途在新结构中的位置和内部编号重排，仍是[PR #198讨论稿](https://github.com/alanthssss/nameless-becoming/pull/198)。先完成内容与稳定ID映射再迁移运行时；保留旧关号、证据、包和存档。
- **节气组织环境，不强制产生24套机制。** 可以改变外观、气候与环境参数；风花、空间和角色的巧妙组合可以独立于节气。暂不调整核心玩法，不能因内部节气标签暗改基础操控或加隐藏惩罚。
- **玩家看见世界变化，不直接读到季节／节气名。** 标题、选关、HUD、对白、过场和回看以地点与情境表达；用光照、植物、风雨、生物、声音及紧张／舒展的节奏承接变化。内部策划／调试可保留标签，既有角色“小满”仍是人名。
- **手绘方向稳定，结构与自然关系可信。** 执行[GDD§8.1](swarm-flight-gdd.md#visual-production-rules)：同屏笔触、比例、材质和光照协调，植物有连接，重物有支撑，挂件有悬点，风雨与遮蔽有可见因果；外观与碰撞／通行规则一致。旧布艺原型规范仅作历史资料。
- **先稳元素，再铺关。** 保留完整体验的目的与用途约束，但不以完成整关作为修好元素的前提；按2026-10-28最新要求制作完整GDD所需元素，分批稳定后组合，不以单一样件缩小总范围。优先修复、复用既有资产和实现，不为本流程重写整个资产系统。
- **24节气各有不同花卉，先核自然条件。** 2026-10-30 Alan要求冬季及各节气不能复用同一种花仅换色/加雪；按种类、自然花期、室外生境、株形/叶形/花序制作。室内允许纳入后续设计；采用时必须一起落实入口/出口与空间连续性、镜头/比例、光照、天气/风/声音边界、进出控制和存档恢复。当前尚未落实这些场景条件，不能仅凭“室内”假设证明素材适用。地点按场景选择，不再等待统一地域；具体花种尚未全部确定，中国水仙可列大寒对应冬末时段候选，须核实所用场景的适生条件。节气名称只作内部标签，不强制新增24套机制。
- **地点可变化，以有代表性的自然美景选景。** 2026-10-30 Alan确认不限制统一地点；不同关卡或场景可以采用不同地点，同一地点也可复用，不要求24关对应24个不同地点。自然一致性按每个场景的地点参考、时段、气候与生境核对，不能把不同地区的花期拼成同一地点的自然日历。保持统一手绘方向、角色尺度与核心操作；相邻空间连续连接，跨地点以清楚的转场交代变化，不把远隔的景观硬接成相邻地形。
- **原边界不重置。** 200＋40小时控制、集中修订历史及北京时间2026-10-29检查点保留；历史累计与可靠剩余未知时明确写未知。24关目标不自动批准额外预算、量产或商业日期变更。

**选景决定的落实：** Codex在#215／#225对应场景首次制作检查点，将地点参考、内部时段、气候／生境、花种及花期资料、构图参考和进出衔接记入原元素／组合记录；不另建队列。验收检查同场花期与环境是否相容、原生尺度下画风／光照／比例是否统一，以及跨地点或室内外切换时天气、声音、控制和存档恢复是否连续。缺证的花种仍为候选；若自然条件冲突或切换破坏可读性，重选该场景搭配，不恢复全作统一地域的前置条件。该决定放开选景范围，不代表已有24关实现或素材验收通过。

## 2. 六个阶段与放行门禁

P0—P5是产物成熟度，可以跨多个工作段。每个阶段的门禁只放行表中限定范围；提交、PR、CI、文档数量或一次任务结束都不使阶段自动升级。

| 阶段 | 目标与输入 | 必须留下的产物／证据 | 放行门禁 | 失败时处理 |
| --- | --- | --- | --- | --- |
| **P0 范围与失败基线** | 读Now、用户约束、实际分支与已有版本；先列本批完整必需元素／组合覆盖清单，再选择一个元素分段验证；叶棚只是首样件 | 冻结源版本、使用位置、实机原始画面／操作；具体缺陷与期望关系；本段修改边界和不动项 | **G0：** 有可重现失败，或有实机基线证明当前形态及待验证范围；两者都须明确样件边界。根因仍可待查，不能从“代码分散”直接断言根因 | 留在P0，取证或缩小问题；不开始批量生成 |
| **P1 单一标准元素** | G0通过；以原素材或已认可方向修一个样件 | 可编辑源／确定性构造、引擎内样件、实际尺寸；默认形态及已有使用状态的原始媒体与定向检查 | **G1：** 原生尺度下风格、比例、连接／支撑、显示与作用一致；适用的状态、进出和恢复无已知基本缺陷。大图漂亮或代码通过不足以放行 | 留在P1修源；发现范围／根因不符则退P0；不复制到更多场景 |

## 3. 门禁怎样记录、由谁判断

每个G0—G5记录以下五项即可，沿用回执保存；GitHub issue链接结论，不另造验收系统：

1. **输入基线：** 批次、元素／关卡ID、源提交及相关素材／配置版本。
2. **目标产物：** 本次解决的具体问题、适用范围和不动项。
3. **实际证据：** 命令／日志、原生图像／连续媒体、场景与操作条件、检查者；未运行明确写未运行。
4. **结论：** `未检查 / 需修复 / 通过`，附理由和残留限制；N/A只用于确实不适用的子项。已知基本缺陷或缺少必要证据不能记通过。
5. **唯一下一动作：** 继续哪个阶段、修改哪个对象、期待看到什么；从回执链接回Now。

Codex主任务是整合者与门禁记录责任人；允许一位限定范围的独立复核者，无嵌套、同一因果链只有一个写者。G1—G3由内部实际检查放行，沿用已认可审美方向；Alan不逐件代验基础问题。需要换画风、改核心、改变预算／商业范围时才形成具体取舍。G4内部候选不等于Alan接受；`accepted`仍须真实反馈，陌生玩家证据单列。

自动检查负责文件、结构和已定义行为；原生视觉检查负责结构、风格、运动与可读性；连续试玩负责理解与节奏。任何一种不能代替另外两种。冻结之后改动影响读图、因果或规则，相关证据必须重新取得；熟悉解法者的复测不能改称首次探索。

## 4. 元素的生产与修改规范

### 4.1 一个可复用元素至少交接什么

不强制增加新文件格式；在既有素材记录和批次说明中保留：

| 内容 | 最低要求 |
| --- | --- |
| 身份与用途 | 稳定ID、版本、装饰／实体／交互职责；已知使用位置 |
| 源与产物 | 可编辑源图／分层／构造脚本、导出素材、生成／来源记录与使用条件；旧源可恢复 |
| 视觉与结构 | 实际显示尺度、视角、比例、笔触、光照；根、枝、悬点、支点、遮挡关系与相关锚点 |
| 行为与范围 | 实际需要的状态和相关碰撞／遮雨边界；允许修改的参数、有单位的范围及禁止变形；不适用的规则说明原因 |
| 版本与证据 | 固定配置／随机种子（如有），导入设置、验证场景／条件、原始媒体、测试结果、已知限制 |

新造型可生成候选；相关资产以已选样件为参考作受控编辑，固定通过的结果并复用。同一提示词反复生成并不作为稳定性验收方法。刚性结构、茎叶连接和绳端点可以采用可编辑构造；具体技术服从当前画风、问题证据和修改成本。

### 4.2 稳定性与自然规律

- 在真实游戏尺寸和同屏背景下检查，不能只放大看素材。使用状态中的体积、比例和连接不得无故跳变。
- 植物的根／茎／枝叶连接、叶棚的支撑和牌绳的悬点必须可解释；重力、风、雨源、遮蔽、碰撞与画面保持一致。幻想规则可以存在，但需稳定可读。
- 缩放／翻转／弯曲必须保持声明的锚点和作用边界。新用途超出允许范围时先补验证，不在关卡里悄悄拉伸补洞。
- 环境参数变化先有可读表现，再产生对应影响；未实现的温湿度作用不隐藏扣体力。季节不等于固定增难，低压片段和结尾保留舒展。
- 随机装饰必须能复现检查条件，且不能破坏连接、关键视线或作用边界。文件规格正确不能证明实际画面自然。

### 4.3 把返工留在源元素

发现缺陷→保留失败样本→定位源／变体／组合／关卡层→在最小范围修复→复测失败项→检查受影响使用点→冻结新版本→受控更新实例。不要重新生成整个场景修一个元素，也不要未经检查让共享源的改动自动替换全部已验证场景。

关卡位置和元素定义分开管理；优先利用现有节点／脚本／资源能力，不为此建立通用编辑器。修改时记录影响面和恢复方式。一个阶段的失败可能使依赖它的后续证据失效，须标记需复查；无关证据保留，不机械重跑全部内容。

## 5. 工作段与可调整交付目标

**2026-10-30 Alan澄清：十分钟是暂定、可调整的任务交付目标，不是游戏时间，也不是到点强制中断。** 目的在于避免单个任务长期没有可检查成果；不能反复为了卡时间只交文档和交接。此决定取代本文、旧Now及旧issue正文中“每完整回合必须<10分钟、9分30秒结束”的硬规则，历史实际超时记录仍如实保留。

开始时选一个具体产物与验收范围，预计过大则按可独立检查的结果拆分。接近十分钟报告已完成产物、剩余检查和调整理由；已有实际制作进展时可调整该段目标以完成必要验证、PR和收尾，不需为可逆实现反复询问。不能借调整无限加范围，旁支问题进入已有issue。

读取、工具等待、并行审查及收尾都计入真实交付耗时；区分墙钟、活跃投入、账单与未知历史。只能观测部分时段时注明覆盖，不能把切换阶段伪称重新开始了一次用户回合。每段至少保存真实产物、原始证据、门禁结论和唯一下一动作。

90秒没有产物、检查或有效发现，或相同方法失败两次，保存现场、缩小问题或换方法。测试命令仍设置合理超时，不能遗留无主进程。自动接续继续暂停，本次澄清不恢复自动化。
